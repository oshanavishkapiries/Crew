# Crew Design Doc

Crew is a CLI tool that turns AI coding agents (Claude Code, Codex, Antigravity) into **a tool-independent dev team with its own memory**. It runs a local web Task Board, spawns agents, verifies their work and merges it into the main branch.

> **Positioning:** Paste one prompt and your team is ready. Memory, roles and workflow live in `crew`, not in the AI tool.

## Idea and goals

- **One subscription, a whole team.** A developer with only a single AI subscription can still run, say, 5 Claude Code sessions as a team with an Orchestrator, Backend, Frontend, QA and Reviewer.
- **Tool-agnostic.** Memory, persona, roles and workflow all live in `crew`, so nothing is lost when a session stops or when the tool is switched from Claude to Codex. An agent is just a replaceable worker.
- **The simplest possible connection.** No MCP config, no editing CLAUDE.md / AGENTS.md. Paste the prompt generated by the Board and the agent connects.
- **Structured orchestration.** The Orchestrator receives its workflow from `crew` itself and follows the phases grill → spec → tickets → dispatch → integrate.
- **Local Task Board** (web UI) with Workspaces, Boards, live agent output, diffs and approvals.

## The core problem

CLI agents (Claude Code, Codex) work turn by turn, so "wait in the background until a task arrives" is not something they can do naturally.

- Bash commands have a timeout (a few minutes).
- Every poll costs context and tokens.
- If the session stops, the loop stops too.
- If one session handles many tasks, its context fills up and gets compacted.

**Solution:** Spawn mode is the default. The crew server spawns a fresh agent process for each task. Pull mode exists only for those who need it.

## Approaches compared

| Approach | Pros | Cons |
| --- | --- | --- |
| REST API + curl prompt | Works for everyone, easy setup | JSON/quoting mistakes, context fills quickly |
| MCP-first | Typed tools, schema validation, role-based permissions | Config differs per tool, the "wait for a task" problem remains |
| Headless spawn only | Parallel, fresh context, lifecycle control | Agents still need a way to communicate |
| **crew CLI + Spawn-first (chosen)** | One tool, every agent has Bash, no MCP config, crew controls the lifecycle, server-side verification | Adapters and permissions must be built carefully |

## Release policy

- **No MVP.** Every feature below must be at a superb level in the very first public release.
- **Full quality, controlled scope.** Tools supported at launch: **Claude Code + Codex**. The Antigravity adapter is added once its headless interface is confirmed.
- No public release until all 8 build milestones are complete and an end-to-end test on a real project succeeds.

│                          crew server                                 │

└───────▲──────────────────────▲───────────────────────▲───────────────┘

 ┌──────┴──────┐        ┌──────┴──────┐         ┌──────┴──────┐

The Board UI, runner and agents all talk through the crew server. Agents never connect to each other directly.

## Agent lifecycle

### Spawn mode (default)

1. The scheduler picks a dispatchable task (dependencies `merged`, budget available).
2. The worktree manager creates a branch + worktree for the task.
3. The runner spawns the agent process inside a PTY through the adapter. Persona, role, relevant memory and task context are injected into the prompt.
4. The agent calls `crew update / ask / remember / done`. PTY output streams live to the Board.
5. After `crew done`, the verification gates run. The process ends; the next task gets a fresh process.

### Pull mode (optional)

- For people who want to keep the agent in their own terminal session, and for tools without headless support.
- The agent calls `crew next --wait`. The server holds the request for less than the Bash timeout (e.g. 90 seconds) and, if there is no task, returns "call again".
- After every `crew done`, the response instructs the agent to "clear your context now and run `crew join` again". Since memory lives in crew, nothing is lost.
- Heartbeat: if there is no `crew` call for X minutes, the agent is shown as "stale" on the Board and its task is re-queued.
- Verification gates apply fully in Pull mode too.

## Commands

### Human / server commands

| Command | Purpose |
| --- | --- |
| `crew start` | Starts the server + Board UI (localhost:4000) |
| `crew init` | Creates `crew.config.ts` in the repo (verify commands, roles, limits) |
| `crew stop-all` | Stops all agents (kill switch) |
| `crew status` | Agents, tasks and budget status |

### Agent commands

| Command | Purpose |
| --- | --- |
| `crew join --token <t>` | Connects and receives persona, role, rules, workDir and memory |
| `crew next` / `crew next --wait` | Gets the next task and its context (Pull mode) |
| `crew update "..."` | Reports progress |
| `crew ask "..."` | Publishes a question to the Board; the task becomes blocked |
| `crew remember "..."` | Saves a learning to role memory |
| `crew done --result "..."` | Sends the task to verification |
| `crew phase` / `crew phase done --output <file>` | Orchestrator only: gets / completes the current workflow phase |
| `crew ticket create ...` | Orchestrator only: creates a ticket with dependencies and acceptance criteria |
| `crew assign <agent> <task>` | Orchestrator only: assigns a task to a role / agent |

### Sample connect prompt

```markdown
You are a member of a software team coordinated by the `crew` CLI.

1. Run now:  crew join --token a8f3k2
   This gives you your role, persona, rules, working directory and project memory.
   Follow them strictly. Work ONLY inside the given working directory.
2. Get work:       crew next --wait   (call again if it returns no task)
3. Progress:       crew update "..."
4. Questions:      crew ask "..."     (then wait for the answer)
5. Learnings:      crew remember "..."
6. Finished:       crew done --result "..."
   Your work will be verified automatically. If it fails, fix it and run crew done again.
7. See `crew --help`.
```

## Code isolation: one worktree per task

- When a task moves to `doing`, a `crew/<task-id>-<slug>` branch and a worktree under `~/.crew/worktrees/<workspace>/<task-id>` are created automatically.
- The agent's `workDir` is that worktree. Permissions deny writing outside it.
- When the task is `merged` or `cancelled`, the worktree is cleaned up. `crew worktree gc` removes abandoned ones.

## Task state machine and merge pipeline

```text
todo → ready → doing → verifying → review → merge-queue → merged
                 ▲         │           │          │
                 └─failed──┘           │          └─conflict → rebase task
                 ▲                     │
                 └──changes requested──┘
        blocked (crew ask) ↔ doing
        escalated (retry limit exceeded) → human
```

- **ready:** A task becomes `ready` only when all its `blockedBy` dependencies are `merged`.
- **verifying:** Server-side verification gates (below).
- **review:** A Reviewer agent checks the diff against the acceptance criteria. On "changes requested", the task returns to `doing` with feedback.
- **merge-queue:** Merges happen one at a time. Before each merge the branch is rebased onto the latest main and the verify commands are re-run.
- **conflict:** If the rebase conflicts, crew automatically creates a "rebase + resolve" sub-task and gives it to the same role that did the original task.
- **Merge strategy:** squash merge by default (one commit per task), configurable.

## Verification gates

After `crew done`, the server checks the work itself instead of trusting the agent's word:

1. **Diff check:** are there changes in the worktree, and were any files outside it modified?
2. **Commands:** lint, typecheck and test commands from `crew.config.ts` (with timeouts).
3. **Acceptance criteria:** a Reviewer agent checks the criteria produced in the spec phase.

On failure, the task goes back to the agent with a summary of the error output. When a task exceeds its max retries (default 3), it becomes `escalated` and is surfaced to the human on the Board.

## Memory system

| Layer | Contents | Injected into |
| --- | --- | --- |
| **Project** | Spec, architecture decisions, conventions, glossary | Every task (as a summary) |
| **Role** | Role-specific notes, past mistakes | Agents of that role only |
| **Task** | Parent task, results of dependencies, relevant files, messages, previous verification failures | That task only |

- `crew remember` saves to role memory. During the integrate phase the Orchestrator reviews these and promotes them to project memory.
- Injection stays within a context budget: project memory summary + role memory + task context. Not everything is included.
- Memory can be viewed and edited from the Board.
- Because conventions (code style, naming) live in project memory, a mixed Claude + Codex team still writes consistent code.

## Orchestrator workflow (phases)

The workflow lives on the server under `src/workflows/`, so it works with any AI tool. No tool-specific skills need to be installed.

| Phase | What it does | Output | Human gate |
| --- | --- | --- | --- |
| 1. Grill | Asks the user about requirements, constraints and edge cases (via chat on the Board) | requirements notes | Yes |
| 2. Spec | Writes the spec: goals, non-goals, architecture, acceptance criteria | spec.md → project memory | Yes |
| 3. Tickets | Breaks the spec into tracer-bullet tickets with dependencies and acceptance criteria | ticket list | Yes |
| 4. Dispatch | Distributes tickets across roles; the scheduler dispatches them | running tasks | No |
| 5. Integrate | Answers questions, unblocks tasks, promotes memory, final check | release summary | Yes |

- Phases can be customised from the Board (add or remove phases, toggle gates).
- At a human gate the Orchestrator process stops. On approval, the phase output is injected into memory and a fresh process is spawned for the next phase.

## Board UI

- **Board view:** state machine columns, dependency arrows, agent avatars.
- **Task card:** live PTY terminal (xterm.js), live `git diff`, commits, verification results, messages.
- **Questions inbox:** answer `crew ask` questions right from the Board; the spawned agent resumes with the answer.
- **Phase approvals:** review, edit and approve the spec and tickets.
- **Agents view:** connected / running / stale / rate-limited status, persona editor.
- **Memory view:** view and edit all three layers.
- **Budget bar:** parallel agents, retries, runtime.
- **Stop all** button.

## Budget, safety and permissions

- **Subscription awareness:** max parallel agents (default 3). When an adapter detects rate-limit errors, that tool's agents auto-pause and retry with backoff. The Board shows "rate-limited".
- **Loop protection:** task depth limit (sub-task of a sub-task), max retries per task, max runtime per agent run, max tickets per phase.
- **Timeouts and kill:** processes that exceed max runtime or hang without output are killed and the task is marked `failed`.
- **Permissions:**
  - Spawned agents may edit and run commands inside their worktree, and run `crew *` commands.
  - `git push`, writing outside the worktree and destructive commands are denied.
  - "Everything allowed" mode is only granted inside the worktree.
  - In Pull mode, the connect prompt tells the user to add `crew *` to the allowlist.

## Tool adapters

Each AI tool gets an adapter. Adding a new tool means writing one adapter.

```ts
interface AgentAdapter {
  id: "claude-code" | "codex" | "antigravity";
  detect(): Promise<{ installed: boolean; version?: string; headless: boolean }>;
  buildSpawn(opts: {
    prompt: string;          // persona + memory + task context
    workDir: string;         // task worktree
    permissions: PermissionProfile;
  }): { command: string; args: string[]; env: Record<string, string> };
  parseOutput(chunk: string): AgentEvent[];   // tool calls, errors, completion
  isRateLimit(event: AgentEvent): boolean;
  installExtras?(workDir: string): Promise<void>; // optional, e.g. Claude Code hooks
}
```

- **claude-code:** `claude -p` headless, allowed/denied tools flags, optional Stop hook (prevents stopping before verification passes).
- **codex:** `codex exec`, sandbox / approval flags.
- **antigravity:** after its headless interface is confirmed. Until then, Pull mode only.

## Tech stack

- **Runtime:** Node.js + TypeScript (CLI + API + UI + runner in one process)
- **CLI:** `commander`
- **Server:** Hono + SQLite (`better-sqlite3`) + Drizzle (migrations)
- **Runner:** `node-pty` (PTY spawn), `execa` (verify commands)
- **Git:** git CLI wrapper (worktrees, rebase, merge)
- **UI:** Vite + React + xterm.js, built and served by the server itself, live updates via SSE
- **Testing:** Vitest + a fake adapter (test the full pipeline without real agents)
- **Distribution:** `npx crew`

## Build milestones

The release is a single superb version, but it is built in this order. Each milestone is the foundation for the next.

1. **Core:** server, SQLite, full data model, task state machine, fake adapter.
2. **Runner:** adapter interface, Claude Code adapter, PTY spawn, timeouts, worktree manager.
3. **Verification:** gates pipeline, retries, escalation.
4. **Merge:** dependencies, merge queue, rebase, conflict tasks.
5. **Memory and workflow:** memory layers, injection, `crew phase`, human gates.
6. **Board UI:** live terminals, diffs, approvals, questions inbox, memory view.
7. **Breadth and safety:** Codex adapter, Pull mode, heartbeat, budget, rate-limit handling, permissions, stop-all.
8. **End-to-end:** complete a real project from grill to merge with a mixed Claude + Codex team.

**Release criterion:** Milestone 8 succeeds, the full pipeline tests pass with the fake adapter, and every failure path (verification failure, conflict, rate limit, hung process) is tested.

## Open questions

- After `crew ask`, should a spawned agent resume via a session-resume flag, or via a new process that receives the answer?
- How should `crew.config.ts` be structured for monorepos / projects with multiple verify commands?
